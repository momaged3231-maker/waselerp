## 2. §Dimensions — Where are party/branch dimensions enforced?

| Level | Party dimension | Branch dimension | Evidence |
|---|---|---|---|
| (a) `gl_accounts` columns | ❌ No `party_required` column | ❌ No `branch_required` column | Schema lines 833-849: no party/branch columns on gl_accounts |
| (b) `gl_entries` (journal lines) columns | ✅ `party_id integer REFERENCES parties(party_id)` (nullable) | ✅ `branch_id integer NOT NULL REFERENCES branches(branch_id)` | Schema lines 895-896: party_id nullable, branch_id NOT NULL |
| (c) `gl_mappings` rules | ❌ Maps concept → account only. No dimension enforcement. | ❌ No dimension enforcement. | Schema lines 853-858: mapping_key, account_id, description only |

**Conclusion:** Dimensions are enforced at the **`gl_entries` (journal line) level**:
- `branch_id` is NOT NULL (schema-level enforcement — every journal line must have a branch).
- `party_id` is nullable in schema, but **code-level enforcement** via posting engine (same pattern as AR/AP: `requireMapping` + posting code populates `party_id` when needed).

**Implication for GRNI:** 
- Branch: schema-enforced (NOT NULL) — every GRNI entry has a receiving branch.
- Party (supplier): code-enforced — posting engine populates `party_id` when posting GRNI, same as AP entries.
- This mirrors how AP/AR/VAT work today. No new mechanism needed.
