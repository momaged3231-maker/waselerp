# E3 — الرسوم والعمولة البنكية الآلية (Bank Fees & Commissions Automation) — مواصفات تنفيذية

> **الحالة:** تصميم فقط — مُجزأة جزئيًا في الكود الموجود (recurring_journals موجودة كوحدة تشغيل آمنة بتداخل يدوي)
> **الأولوية:** متوسطة · **التعقيد:** متوسطة · **الأثر المحاسبي:** مباشر على المصروفات البنكية

---

## 0) ما هو موجود فعليًا في الكود الآن

| البند | يوجد؟ | التفصيل |
|---|---|---|
| `recurring_journals` + `recurring_journal_lines` | ✅ | فقط قالب ثابت يحدده الإنسان يدويًا بسعر ثابت وتكرار ثابت؛ لا قاعدة لا تصلح للرسوم البنكية المتغيرة/الشهرية الحقيقية |
| `POST /accounting/recurring/run` | ✅ | ينفذ كل القوالب المستحقة؛ بدون بنك scrapbook ولا مصدر خارجي |
| `bank_statement_lines` | ❌ | لا استيراد كشف بنكي، لا لاختلاف رسوم بنكية عن حركة برعاية نفسها |
| ربط كشف البنك الآلي بقيد `5107` رصيد | ❌ | لا — على المحاسب كتابة القيد يدويًا كل شهر |
| حساب `5107 مصروفات مالية` و `5103 مصروفات إدارية وعمومية` | ✅ | موجودان بالمخطط بلا آلية consumed تلقائية |
| `other mapping OTHER_INCOME` / `OTHER_EXPENSE` | ✅ | يمكن استهدافهما لكن بدون جدول rules |

## 1) مطابقة المستخدم في هذه المهمة لتحديد E3

قال الوكيل في جلستين متسارعتين:

> الـ E3 = الرسوم والعمولة البنكية الآلية — "قائمة expenses سببها 10xxx تلقائية"

هذا يعني **ليس** "Create New Feature" بالمعنى التقليدي. له معنى واضح: المستخدم يريد قائمة من القواعد التي تنتج قيد تلقائي للمصروف المتكرر كل شهر (رسوم النت، رسوم السويتش، عمولة جهاز POS، عمولة ضريبية سوق السيارات، ...إلخ). الشريحة: "تُولد محاولات مرة من عند النظام دون Intervention المحاسب".

## 2) الهدف

1. نظام **recurring expense rules** يختزن اسم القاعدة، المبلغ الثابت (أو نسبة)، حساب المصروف، تكرار (شهري/ربع سنوي/سنوي)، يوم الشهر، حساب البنك الذي يُخصم منه (`cash_accounts` type=2)، والمستفيد (الاسم فقط — نصي لا حاجة لحساب).
2. جدولة **cron** يومي: كل يوم يتم فحص القواعد المستحقة لـ (اليوم `day_of_month`)، وتوليد `recurring_journals` عنها بقيمة ثابتة، بنفس آلية `runRecurring` الحالية.
3. **فرضية الالتزام**: كريديت البنكي يُسجل انصراف للبنك فقط (automation دون طرف خارجي).
4. حماية محاسبية كاملة: نفس `assertPeriodOpen`، نفس `postJournal` الصارمة، لا يوفر احترام `periods.is_closed`.
5. **بدون تدخّل في أي من وحدات POS/المبيعات/المخزون** — هذا قيود محاسبية بحتة.

## 3) نموذج الأحداث

| الحدث | الجدول/الحركة | المعنى |
|---|---|---|
| إنشاء هدف rule | `bank_expense_rules` (عائلة جديدة) | نقطة بداية مرجعية |
| توليد قيد من rule | ينشأ سطر في `recurring_journals` + `recurring_journal_lines` | نفس آلية القوالب الحالية |
| عكس rule | `rule.is_active = false` (لا يُولد مرة أخرى) | التحكم، لا حذف |
| تنشيط rule | `is_active` flipback من DB | بالإدارة يدويًا |
| رصيد rule موقوف مؤقتًا | `suspended_at` + `suspended_reason` | بدون قراءة source of truth |

## 4) التغييرات على قاعدة البيانات

```sql
CREATE TABLE IF NOT EXISTS bank_expense_rules (
    rule_id             integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    branch_id           integer NOT NULL REFERENCES branches(branch_id),
    name                text NOT NULL,                      -- 'رسوم POS الشهرية'، 'عمولة البنك التجاري'
    description         text,
    bank_account_id     integer NOT NULL REFERENCES cash_accounts(cash_account_id),
    expense_account_id  integer NOT NULL REFERENCES gl_accounts(account_id),
    amount              numeric(18,2) NOT NULL CHECK (amount > 0),
    frequency           smallint NOT NULL DEFAULT 1,        -- 1 شهري · 2 ربع سنوي · 3 نصف سنوي · 4 سنوي
    day_of_month        smallint NOT NULL CHECK (day_of_month BETWEEN 1 AND 28),
    start_date          date NOT NULL,
    end_date            date,                               -- NULL = مستمر بغير نهاية
    counterparty_name   text,                                -- اسم الطرف المستفيد (للتقرير)
    is_active           boolean NOT NULL DEFAULT true,
    suspended_at        timestamptz,
    suspended_reason    text,
    created_by          integer REFERENCES users(user_id),
    created_at          timestamptz NOT NULL DEFAULT now(),
    updated_at          timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS ix_bank_expense_rules_branch_day ON bank_expense_rules(branch_id, month, is_active) WHERE is_active = true;
```

## 5) القيود المحاسبية المتوقعة

### 5.1 — النظام يولّد نفس آلية `recurring_journals`:

```
Dr  <expense_account_id>     [amount]    الرسوم الشهرية / البنك X
Cr  <bank_account_id> (GL)   [amount]    من حساب فرع X
```

### 5.2 — الربط بمستوى كشف البنك (E1):

عند تفعيل E1، كشف البنك يُكتشف للـ subscriber بـ "رسوم POS 500 EGP" — يُطبق `matching_rules` تلقائيًا (`pattern = '*POS*' / bank_account_id = X`) → قيد من rule. لم يوجد → تثبيت قضية manual cleanup (`status = 10 draft`).

### 5.3 — إذا كانت الفترة مغلقة:

`runRecurring` لا يُنفذ `recurring_journals` بتاريخ داخل `periods.is_closed = true` → يُسجل رفض ولا يتدخل E3؛ فتح الفترة من خارج النظام يدويًا (منشور E6).

## 6) الصلاحيات

| الدور | الصلاحية |
|---|---|
| مدير النظام | إنشاء/تعديل/حذف rule (بحيلة `deleteGuard('bank-expense-rules')`) |
| محاسب (Accountant) | عرض rule، قبول/رفض التوليدات |
| كاشير | لا تصل لـ Bank Expense Rules |

## 7) قواعد التحقق

1. **مبلغ Rule يجب أن يكون >0** — للرصيد الصفري: rule غير مسموح (لا يفيد إلا كبديل placeholder)
2. **الفرع المغلق**: `periods.is_closed` ورمز `day_of_month` و `start_date` — لا تُنشئ rule بغض النظر إذا كانت الفترة مفتوحة؛ الإنشاء بضمان لا بمنع.
3. **المبلغ حصري**: تقيل نفس `bank_account_id` خلال`rule`.
4. **النطاق الزمني**: `end_date < start_date` → 400 برسالة `تاريخ النهاية لا يمكن أن يكون قبل تاريخ البداية`.
5. **لا تعديل على rule مجدول** من دون `refuse` واضح: تعديل المبلغ بعد الجدولة = ممنوع بحكم `delGuard`.
6. **طابع Rule يستهلك مرة وحيدة** يوم أيامه فقط؛ غير/تصادلي إذا الفترة مغلقة: القواعد رفض لا تتراكم.
7. **تناسخ مع `other_expense` (5106/5107) أو `other_income` 4104**: rules مبهمة الوزن خارج السياسة ترفض.

## 8) الـ API

```
GET    /accounting/bank-expense-rules?branch_id=   — كل القواعد
POST   /accounting/bank-expense-rules               — rule جديد
PUT    /accounting/bank-expense-rules/:id           — تعديل وحسب الحالة
POST   /accounting/bank-expense-rules/:id/deactivate  — توقيف (is_active=false)
POST   /accounting/bank-expense-rules/:id/resume     — استئناف
POST   /accounting/bank-expense-rules/run             — تشغيل يدوي لاستثناء كاستثناء للتجهيز من cron
GET    /accounting/bank-expense-rules/:id/preview    — preview: سطور القيد المتوقع (غير قابل للتخزين)
```

## 9) التقارير

1. **تقرير القواعد البنكية النشطة** — جدول: Name · Bank · Amount · Frequency · next_date · آخر توليد
2. **تقرير القيود المولدة هذا الشهر** — نفس تقرير `runRecurring` ولكن مرتبة حسب قسم Bank Expense
3. **تقرير Rule التي لم تتولّد** — لسبب (لم Reach`day_of_month)` / الفترة المغلقة / الـ rule disabled) — بمجرد التراحع من 1-scope claim على الادміні
4. **تقدير الرسوم المتوقعة للربع القادم** — استناداً للقواعد النشطة (لا الحقيقة، لكن تقريب سنوي × مراجعة)

## 10) الاختبارات الآلية (Regression)

| الاختبار | ما يرى |
|---|---|
| `bank-expense-rules.create` بمبلغ 500 → يوم 15 → 1 قاعدة | فقط قاعدة، لا قيد ورقة منفردة بمعنى alternating |
| `cron run` في يوم 23 من كل شهر | يُولد القيد: Dr 5107 / Cr Cash_bank GL 1102 بقيمة 500 |
| `day_of_month` بعد التاريخ المراد | لا يُولد |
| الفترة مغلقة في اليوم المستحق | يُرفض برسالة واضحة `«الفترة مغلقة»` |
| مناسبة repeat 2 مرات على صرف موظف | `recurring_journals` مرتين عن نفس التاريخ بعلامة بنكية |
| القاعدة مقروءة مرتين من الـ cron في نفس اليوم | فقط واحدة من القيدين تُلصق؛ الثانية تُضبط |

## 11) خطوات التنفيذ (8 خطوات)

1. تطبيق الـ DDL على قاعدة اختبار — `tools/pg/migrate-all.js`
2. `bankExpenseRulesSlice` — تجنيد الـ rules + preview + run بنفس نمط `recurring_journals`
3. معدّل returns augmentation: `Post /bank-expense-rules/run` يضيف قائمة بال`generated[]` مع `journalId`
4. cron: نفس store pattern إن وُجد — إن لم تجد — سكربت CLI `node tools/pg/bank-expense-cron.js` يجدول مثل `tools/pg/restart-api.sh` يطفو. الـ cron介入 يوميًا آمن (read-only للفحص). خطير ذُفّ أن cron للانتظام: `"scheduler": {"enabled": true, "timezone": "Etc/Cairo"}`
5. bank expense rules endpoint — نفس NodeJS gating isolation على نفس النسق الخاص بـ `recurring_journals`
6. UI سك حالتين: `الإعدادات ← الرسوم البنكية` (القوائم + استنساخ + توليد) تحت `/settings` بجانب تبويب «إقفال الشهر» (E6)
7. نضيف 3 قواعد في اختبار أول واحد — رسوم WP, رسوم S Mage, عمولة POS — يتم اختبارها automation
8. حيث وُجد NodeJS single-process اختبارية: `smoke-test.js` تختبر `/bank-expense-rules/run` وغيره

## 12) ما الذي لا أفعله

- لا أخلق "أي رسوم بنائية وتلقائي عن إلا ويمكن لتحديد محاسب واحد من قبل من قبل" — أوراق rate غير مسموح
- لا أجرب broadcast على كل فروع الشركه بلا سقف — كل Rule تكتفي <حساب واحد>
- لا أدمج مع E4 (العلم): لا أكسر إشعار "استلم كاش في مسألة واحدة" بأي سيناريو
- لا أدخل `5108` هنا (هو للإهلاك الأصلي الثابت في E5) — E3 للانقد الآن فقط
