# E4 — إشعارات استحقاق العميل (Customer Statement Notifications) — مواصفات تنفيذية

> **الحالة:** تصميم فقط — غير مُنفّذة في الكود بالكامل (الإشعارات بضاعة في النظام محدودة جدًا)
> **الأولوية:** متوسطة · **التعقيد:** متوسطة · **الأثر المحاسبي:** صفري (لا قيود) — **الأثر العملائي:** منهجي

---

## 0) ما هو موجود فعليًا في الكود الآن

| البند | يوجد؟ | التفصيل |
|---|---|---|
| `parties` مع `phone`, `mobile`, `email` وغيره | ✅ | الأعمدة موجودة وممكّنة |
| `customer_groups` + `classification` | ✅ | تجميعات التصنيف موجودة |
| `crm_leads` ↔ `crm_activities` ↔ `crm_tickets` | ✅ | مهام بشرية: اتصال/زيارة/بريد يدوي؛ كتالوج في الذاكرة |
| `reminders` | ✅ | تذكير خاص بالموظف نفسه |
| `vouchers` (سندات قبض) + `voucher_allocations` | ✅ | يتم تسجيل السداد ولكن لا إبلاغ العميل به |
| `postJournal` أرصدة العملاء | ✅ | `1103` ذمم مدينة — يجب أن تُكرر بالخصم بعد السداد |
| أي إرسال بريد/واتساب/SMS | ❌ | لا توجد قناة إرسال |
| `ETA مصر` / `ZATCA السعودية` (إرسال الفاتورة للهيئة) | ✅ | يتم إرسال الفاتورة للهيئة؛**لا** إشعار للعميل مباشرة |

## 1) الهدف — مأخوذة من فجوة الاكتشاف E4

في قائمة الفجوات: **E4 · إشعارات استحقاق العميل (statement) عبر بريد/WhatsApp · لا توجد إجمعة أتمتة للعميل على الإطلاق**

المستخدم يريد:

1. **حساب استحقاق تلقائي** = `AR debit (open balance) of كل عميل` بنسبة تفصيلية (تاريخ مفتوح لكل فاتورة + ثابتة مرهونة بالحدود الائتمانية)
2. **إرسال دوري (nightly/weekly/monthly)** بالمحتوى المهيأ — من خلال البريد (SMTP) للميل أو WhatsApp للأرقام.
3. **قنوات متعددة**: Email + WhatsApp (عبر WhatsApp Business Cloud API or deep link `wa.me`)
4. **تتبع المنشود مقارنة بالمرسل** — سجل إرسال لكل عميل: آخر إرسال + ردود (إنق) — مقبول بأنه عميل "هل يدفع أم يستلم؟"
5. **منع تجاوز الحد الائتماني**: إذا AR > limit → notification عاجل أو حظر full‑payment ذاتio (إنها E7 بعد ذلك — ليست هذه المرة)

## 2) نموذج الأحداث

| الحدث | الجدول/الحركة | المعنى |
|---|---|---|
| إنشاء قالب محمول (template) | `statement_templates` | المعرف والمحتوى |
| Target pricing | القواعد في `statement_triggers` | من يتلقى؟ |
| Job run | برنامج جدول **يومية 03:00 Cairo** | يخطط على أوضاع الزمن المحلي |
| إرسال | `statement_log` (per customer × last_sent_at × status) | سجل كامل لكل إرسال |
| إلغاء اشتراك | `parties.unsubscribed_statement` أو boolean | الاهتمام بإلغاء الإشعار |
| Spam-report | `parties.statement_reported_at` | بالآني |

## 3) التغييرات على قاعدة البيانات

```sql
CREATE TABLE IF NOT EXISTS statement_templates (
    template_id       integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    code              varchar(60) NOT NULL UNIQUE,          -- 'MONTHLY_AR', 'DUNNING_1', 'DUNNING_2'
    language          varchar(10) NOT NULL DEFAULT 'ar',    -- 'ar' / 'en'
    subject           text NOT NULL,
    body_html         text NOT NULL,                         -- ديناميكي بمتغيرات: {{customer_name}}, {{total_due}}, {{oldest_due_date}}, {{currency}}
    is_active         boolean NOT NULL DEFAULT true,
    created_by        integer REFERENCES users(user_id),
    created_at        timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE IF NOT EXISTS statement_triggers (
    trigger_id        integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    template_id       integer NOT NULL REFERENCES statement_templates(template_id),
    name              text NOT NULL,
    branch_id         integer REFERENCES branches(branch_id),     -- NULL = كل الفروع
    customer_group_ids integer[],                                 -- NULL = كل المجموعات
    min_overdue_days  integer NOT NULL DEFAULT 0,                 -- 0 = حتى entity with zero due
    max_overdue_days  integer,                                    -- NULL = بدون حد
    min_amount        numeric(18,2) NOT NULL DEFAULT 0,
    min_credit_limit_usage_pct integer,                           -- 80 = 80% of limit
    trigger_frequency smallint NOT NULL DEFAULT 1,               -- 1 يومية · 2 أسبوعية · 3 شهرية
    next_run_at       timestamptz NOT NULL DEFAULT now(),
    is_active         boolean NOT NULL DEFAULT true
);

CREATE TABLE IF NOT EXISTS statement_log (
    log_id            bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    trigger_id        integer REFERENCES statement_triggers(trigger_id),
    party_id          integer NOT NULL REFERENCES parties(party_id),
    template_id       integer NOT NULL REFERENCES statement_templates(template_id),
    channel           varchar(20) NOT NULL,                       -- 'email' / 'whatsapp' / 'sms'
    sent_at           timestamptz NOT NULL DEFAULT now(),
    recipient         text,                                        -- email أو رقم هاتف
    subject           text,
    body              text,
    status            smallint NOT NULL DEFAULT 1,                -- 1 sent · 2 failed · 3 bounced · 4 unsubscribed
    error_message     text,
    provider_response text
);

-- روابط customer_group موجودة مسبقاً في customer_groups

CREATE TABLE IF NOT EXISTS statement_unsubscriptions (
    unsubscription_id integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    party_id          integer NOT NULL UNIQUE REFERENCES parties(party_id),
    reason            text,
    unsubscribed_at   timestamptz NOT NULL DEFAULT now(),
    unsubscribed_by   integer REFERENCES users(user_id),
    note              text
);
```

## 4) القيود المحاسبية

**لا قيود** — هذا ميزة تشغيلية وليست ماليّة — إذا فتحت الفواتير وضريبتها AR مدفوعة، لا تتأثر الآن.

أما إن أرادت الإدارة **فورمة Dunning** (جزء من الطلب):

```
Dr  5107  مصروفات مالية    [مبلغ المصاريف المقترحة على العميل]
Cr  1106  مصروفات مدفوعة مقدماً   [مبلغ المصاريف]
```

لكن هذه معاملات لم تكلمت في كود؛ هنا فقط التوجيه. الإدارة تستخدم Rule أولاً بدون رسوم.

## 5) الصلاحيات

| الدور | الصلاحية |
|---|---|
| المدير/المدير التنفيذي | إنشاء templates triggers إلغاء اشتراك |
| محاسب (Accountant) | عرض statement_log فقط |
| كاشير | لا تصل لـ Statement Automation |
| مدير النظام | حذف logs (soft، بـ effective retro) |

## 6) قواعد التحقق

1. **`company.email_unsubscribed`** أو `parties.statement_unsubscribed` — لا ترسل إشعارات لعميل طلب إلغاء
2. **WhatsApp**: فقط للأرقام بصيغة مصرية تبدأ بـ 01 أو 011/012/010 مع البادئ `+20` في wa.me deep link
3. **Email**: address valid & not موثوق بأحداثة دائمة (invalid domain / role address)
4. **سقوف الإرسال**: لا ترسل أكثر من مرة كل 7 أيام لنفس العميل بذات الـ template (تفادي التكرار)
5. **إقرار Security**: البريد يتضمن الهاتف/الرصيد فقط، لا روابط دفع ولا any بيانات بطاقة ائتمان
6. **العملات**: كنصوص صحيحة `{{balance}} EGP` — لا فيجز (co) ترميز عبر Intl.NumberFormat
7. **اللغة الافتراضية**: عربية اسم customer_name · عربية للقوالب · عربية للإشارة AR والتواريخ (هجري هجري)
8. **الفرع المغلق**: لا تُرسل إن `periods.is_closed = true` في الفرعاتالياً
9. **غير-متوازن AR**: لا تُرسل إن `AR balance < min_amount`

## 7) الـ API

```
GET    /customer-statements                    — للقائمة (بفلتر status)
POST   /customer-statements/preview/{party_id} — معاينة المحتوى المرسل للعميل
POST   /customer-statements/run-now            — ربط يدوي محفظة واحدة (management)
GET    /customer-statements/log?party_id=      — كشف كل الإرسالات
POST   /customer-statements/unsubscribe        — إشارات إلغاء الاشتراك
POST   /customer-statements/templates/:id      — تعديل قالب بعناية (create_by=المشهد الإداري فقط w/ confirmation)
GET    /customer-statements/config              — سجل 1103 ديسينغ (قراءة فقط — ببساطة للإدارة)
```

(خاصة `STMP / WhatsApp Flow` لا يُستخدم وقت الـ POST يدويًا — كجزء من working env، هذه مراحل تحضيرية)

## 8) التقارير

1. **كشف الإرسالات** — جدول يوم/أسبوع: المحتوى · قناة · وضع (sent/failed/unsubscribed) · كمية عيدات ب
2. **تقرير العملاء المهملين** (في آخر 90 يومًا، لم تُرسل سابقًا) — في `CRM`
3. **تقرير العملاء الأكثر ملدونتهم** — مصنفة حسب AR balance تنازلي — بكيب قائمة للمحصل/الأدواري
4. **تقرير "هل يدفع أم يستلم؟"** — مع علامات رسوم مربية
5. **تقرير إلغاء الاشتراك** — السبب + تاريخ + العميل + ملاحظة (حويكة)

## 9) الاختبارات الآلية (Regression)

| الاختبار | ما يرى |
|---|---|
| `run by trigger` في يوم 25 → كل العملاء AR > 0 يتلقون | الإرسال وجميع الأوراق سجل في statement_log |
| إلغاء اشتراك عميل → not delivered | لا إشعار له حتى يتسجبل \`unsubscribed_at\` |
| error SMTP رار → status=2 + error_message | لا ينسنجم القائمة، ثابتة ومتراط لا يحشد |
| trigger 2× اختبار "يوم واحد يشتغل" | تشغيل واحد فقط — لا يرسل مرتين في نفس اليوم |
| {{customer_name}} بلا email متوفر | يُفشل القالب، يؤول إلى WhatsApp بالرقم، لا يرمي exception |
| unsubscribe from WEB view | يمكن للعميل نفسه بالرار invoice / statement unrelated |

## 10) خطوات التنفيذ (10 خطوات)

1. تطبيق الـ DDL على قاعدة اختبار — `tools/pg/migrate-all.js`
2. `statementRunner` — service ثم `runBatch()` للتنفيذ
3. SMTP integration — توصيل `process.env.SMTP_*` مع `nodemailer` (نفس نقطة تقنية ETA) لكن `ETA`. الخطوة متوازية لا متزامنة
4. WhatsApp link لا webhook — just `wa.me/{phone}` opened في قصة علامة (بديل USSD/plugin)
5. cron scheduler — عبر `node-cron` في worker أو على نفس الـ `pg_cron` (over-architecture إن لزم)
6. اللغة العربية تقاعد عبر Arabic tokens بدل templates لاختزال البروسبرات
7. UI: نقطة `/customers/:id/statement` — Preview + send + unsubscribe
8. إعداد trigger «MONTHLY 1st of month» أول واحد تشغيلي
9. تقرير unsubscribe/delivered/open — `statement_log` يُبنى على CloudWatch-style (الفهارس جاهزة)
10. توثيق بالتحديد — D33 «E4 Customer Statement» في `docs/EEYES-STEPS.md` مع خطوات التفعيل

## 11) ما الذي لا أفعله

- لا أرسل حقل أيسر `E-Mail` أوراق بيانات بطاقة ائتمانية أو أي معلومات حساسة — يحظر عقود / PCI ONU VOG
- لا أُرسل رسائل تُحدّد الطلب في حالة واحدة إذا كانت ≥ 14 يومًا بدون تاريخ
- لا أصلح أي ملفات استدعائية ملغاة كجزء من هذه المهمة — عدم تدخل في POS أو recurring
- لا أشغّل أوراق SMTP بالتلقائي في مرحلة البناء — فقط في بيئة الاختبار
