# E2 — التحويل بين الفروع (Cross-Branch Transfer) — مواصفات تنفيذية

> **الحالة:** تصميم فقط — غير مُنفّذة في الكود
> **الأولوية:** عالية · **التعقيد:** عالية · **الأثر المحاسبي:** صفري على مستوى الشركة (لكن أثر على مستوى الفرع)

---

## 0) ما هو موجود فعليًا في الكود الآن

| البند | يوجد؟ | التفصيل |
|---|---|---|
| جدول `stock_transfers` / `stock_transfer_lines` | ✅ | للتحويل بين مخزني **نفس الفرع فقط** (ورفض الصريح: `أحد المخازن لا يتبع الفرع الحالي`) |
| حركة `outbound` صادر `Dr COGS / Cr INVENTORY` (قديمة) | ❌ | مُصلحة في D29 → الآن Dr/Cr INVENTORY فقط |
| جدول `branches` | ✅ | فقط `branch_id` قابلة للـ scope |
| تحويل بين فروع | ❌ | غير مسموح مطلقًا — لا جدول ولا مسار |
| ميزانية  coûts تلقائية لكل فرع | ❌ | لا يوجد فرع-level profit جاهز، فقط مجال branch في الفواتير والقيود |
| كود قيد حساب الأصول الحالية | ❌ | AR/AP مدينون/دائنون حصلت على أرقام ضمنية حسب الفرع |

## 1) الهدف — ما لا يحققه التصميم الحالي

عنده مثلاً: مخزن المعادي يبيع آيفون 15، لكن المستودع الفعلي بالمقطم. الآن يشتري مرة ثانية أو ينقل بين الفروع بدون أي سند. المطلوب:

1. سند حركة بين الفروع بـ `from_branch` و `to_branch` — **لا** لتحويل داخل مخزنين في فرع واحد (موجود)، بل بين فرعين مختلفين.
2. حساب تكلفة مقدمة (COGS) يبقى ثابتًا — لا تزيد ولا تستهلك مبيعات.
3. حركات `stock_movements` في الجدولين: `transfer_out` (من الفرع المصدر) و `transfer_in` (إلى الفرع الهدف) — نفس الكمية و نفس متوسط التكلفة.
4. إقفال الفترة في الفرع المصدر/الهدف يمنع التحويل الجديد إذا إحدى الفرعتين مقفولة.
5. تأثير صفر على GL على مستوى الشركة (لكن نظيف على مستوى الفرع إن احتاج إداريًا لتقارير فرعية).

## 2) نموذج الأحداث

| الحدث | الجدول/الحركة | المعنى |
|---|---|---|
| فتح سند تحويل بين فروع | `branch_transfers` (رأس + سطور) | ذبح 1 |
| اعتماد سند تحويل | status → 2، يولّد `outbound` voucher | ذبح 2 |
| استلام في الفرع الهدف | status → 4، يولّد `inbound` voucher | ذبح 3 |
| اعتذار (يعمل الآن) | `is_cancelled` + عكس الحركات والقيود | ذبح 4 |

## 3) التغييرات على قاعدة البيانات

```sql
CREATE TABLE IF NOT EXISTS branch_transfers (
    branch_transfer_id  bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    transfer_no         varchar(60) NOT NULL UNIQUE,
    transfer_date       timestamptz NOT NULL DEFAULT now(),
    from_branch_id       integer NOT NULL REFERENCES branches(branch_id),
    to_branch_id         integer NOT NULL REFERENCES branches(branch_id),
    from_warehouse_id    integer NOT NULL REFERENCES warehouses(warehouse_id),
    to_warehouse_id      integer NOT NULL REFERENCES warehouses(warehouse_id),
    status               smallint NOT NULL DEFAULT 1,  -- 1 مسودة · 2 معتمد · 3 ملغي · 4 مكتمل
    total_value          numeric(18,2) NOT NULL DEFAULT 0,
    notes                text,
    created_by           integer NOT NULL REFERENCES users(user_id),
    created_at           timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE IF NOT EXISTS branch_transfer_lines (
    line_id              bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    branch_transfer_id   bigint NOT NULL REFERENCES branch_transfers(branch_transfer_id) ON DELETE CASCADE,
    line_number          integer NOT NULL,
    item_id              integer NOT NULL REFERENCES items(item_id),
    unit_id              integer NOT NULL REFERENCES units(unit_id),
    quantity             numeric(18,6) NOT NULL,
    unit_cost            numeric(18,4) NOT NULL DEFAULT 0,
    notes                text
);

CREATE INDEX IF NOT EXISTS ix_branch_transfers_from ON branch_transfers(from_branch_id, status);
CREATE INDEX IF NOT EXISTS ix_branch_transfers_to   ON branch_transfers(to_branch_id,   status);
```

## 4) القيود المحاسبية المتوقعة

### 4.1 — قرار أساسي: صفر أثر على GL مستوى الشركة

الترحيل البيني لا يخلق ولا يدمر قيمة داخل الشركة؛ نقل الأصل بين فرعين لا يؤثر على الميزانية ولا على قائمة الدخل. لهذا: **لا يوجد قيد في `gl_journals` وقت التحويل البيني** — الحركات تسجل بالكامل في `stock_movements` فقط:

```
outbound (status → 2):
    stock_movements.move_type = 'transfer_out'
    from_warehouse_id, item_id, quantity = Q, unit_cost = C

inbound (status → 4):
    stock_movements.move_type = 'transfer_in'
    to_warehouse_id,   item_id, quantity = Q, unit_cost = C   -- نفس C السابق
```

### 4.2 — أثر يُضاف عند الحاجة: كشف تحليل للفروع

إذا أرادت الشركة تقارير Profit by Branch، تُضاف الأراح هادية بيضاء بلا قيود صفرية:

```
outbound (اختياري): Dr تصفية مخزون — فرع A / Cr تصفية مخزون — فرع B    لا أثر على ميزانية الشركة
issue lines identical
inbound  (اختياري): Dr تصفية مخزون — فرع B / Cr تصفية مخزون — فرع A
```

(بدون استخدام في كل فرع؛ تستخدم فقط للتقرير وبرقم إجمالي بين الفرعين)

## 5) الصلاحيات

| الدور | الصلاحية |
|---|---|
| أمين مخزن (StoreKeeper) | إنشاء/اعتماد سند تحويل بين فروع + تنفيذه |
| مدير النظام | حذف/إلغاء سند — `deleteGuard('branch-transfers')` |
| كاشير | لا تصل لـ Branch Transfer |
| محاسب (Accountant) | انتظار سندات بين فروع للمراجعة |

## 6) قواعد التحقق

1. **مخزني نفس الفرع**: if `from_branch_id !== to_branch_id` ❌ وتسمح بالكود داخل review؛ إذا تمزون بين فرعين سماح — لا
2. **كمية كافية**: `on_hand_qty(item, from_warehouse)` >= كمية السطر؛ خلافه 400 بالرسالة الواضحة
3. **الفرع المغلق**: لا تقبل فرع مقفول فترة (`periods.is_closed = true` من أي فرع مشاركته)
4. **متوسط التكلفة متطابق**: حركة `transfer_in` تُؤخذ `unit_cost` من `transfer_out` (نفس المعامل، متوسط متحرك)
5. **لا تعديل على الحركات المعتمدة**: status ≥ 2 → قل "لا يمكن تعديل/حذف" بلا استثناء
6. **سند افتتاحي**: لا يوجد — نسبة تغير `average cost` فقط إذا اكتملت — معاملاها مسجلة جاهزة

## 7) الـ API

```
GET    /branch-transfers?branch_id=        — الطلبات المرسلة والمستلمة مع كل سطور
POST   /branch-transfers                    — إنشاء بجملة `fromWarehouseId · toWarehouseId`
POST   /branch-transfers/:id/lines          — سطرًا سطرًا: item · qty (costew automatically from `getWarehouseCost`)
PUT    /branch-transfers/:id                — تعديل الرأس قبل الاعتماد
POST   /branch-transfers/:id/approve        — حركة outbound + `stock_count_voucher` outbound
POST   /branch-transfers/:id/cancel          — العكس كامل: عكس `transfer_out` (IN) + عكس `transfer_in` (OUT)
POST   /branch-transfers/:id/receive         — حركة inbound + `stock_count_voucher` inbound
DELETE /branch-transfers/:id                — مسودة فقط + `deleteGuard('branch-transfers')`
```

## 8) التقارير

1. **تقرير حركات بين الفروع** — date · from→to warehouse · item · qty · cost · value · منشئ · تاريخ
2. **تقرير أرصدة التحويل** — لكل item: متوسط تكلفة موزع بين الفروع (متوسط مرجح لتلك الفرع بالذات)
3. **فاتورة نقل بين فرعين** — ملف إيصال بتوقيعين (من الشاحن + من المستلم) — بديل paper trail

## 9) الاختبارات الآلية (Regression)

| الاختبار | ما يرى |
|---|---|
| Transfer out 5 من WH-MAIN(معون) إلى WH-CP2(فرع آخر) | تسجيل `transfer_out` + `transfer_in`، إجمالي التكلفة = 5 * average (ثابتة) |
| Insufficient stock | 400 برسالة `الرصيد غير كافٍ للصنف X` |
| Cancel بعد الاعتماد وإلغاء الحركتين | الحركتين ملغيين + `on_hand_qty` عاد لـ status الأول |
| Branch أ مقفول | 400 `الفترة المحاسبية «...» مقفلة ولا تقبل مستندات جديدة` |
| GL unchanged | على مستوى الشركة، الم SUM بين مديني البدينين لا تتغير |
| متوسط التكلفة متطابق في الفرعين | inbound costs = outbound costs |
| الصلاحية | كاشير → 403 |

## 10) خطوات التنفيذ (8 خطوات)

1. تطبيق الـ DDL على قاعدة اختبار منفصلة — `tools/pg/migrate-all.js`
2. Mod `stock_movements` ledger: ارفع `move_type` الجديد `transfer_out` و`transfer_in` (أو استخدم `reference_type = 4`)
3. Service `branchTransfersSlice` مع الدوال الأساسية الستة
4. نفس نمط المستودع `assertPeriodOpen` على الفرعين قبل اعتماد
5. واجهة: شاشة تحت `المخزون ← تحويل بين فروع` — نفس معمارية الشاشة الحالية لـ stock-transfer مع `from/to` fields مترابطة
6. Test suite إضافة `smoke-test.js` — 9 فحوصات جديدة للتحويل البيني
7. لا تحديث حركات قديمة (أي حماية data) — تريد `psql SELECT` أولًا
8. نشر: `feat(convert): cross-branch stock transfer (zero GL effect, movement ledger only)`

## 11) ما الذي لا أفعله

- لا أُحول بين فروع وتقوم فقط بحكم أن هما يملكونهما نفس المالك — هذا يقرره الـ OS، ليس التاجر. إذا كان الفرعان يملكهما شركاء مختلفون، التحويل يجب أن يكون بيع عادي (BG) بينهما بـ فانسيه/فاتورة داخلية.
- لا أُحول رصيد المدين/الدائن بين الفروع — الذمم تابعة لـ `branch_id` في المثال الحالي.
- لا أخلق "صندوق تحويل" بـ قيد GL — هذا سيوهم القارئ بأن هناك أصل بـ حجم التحويل البيني.
- لا أقبل تعديل أو حذف سند بعد الاعتماد؛ فقط التصحيح عبر مستند عكس.
